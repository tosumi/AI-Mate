# 運営者の手順書(FureAI ペルソナ v1.5)

作成: 2026-11-25(ドラフト)

この文書は、運営者のアカウントの追加と外し方、MFA の扱い、AI の応答への報告の確認の手順をまとめたものです。漏えいが疑われるときは、[漏えい時の手順書](breach-response.md)に従います。

## 1. 前提

### 1.1 運営者の画面と API

- 画面: Web のサイトの`/ops`(一般ユーザーの画面からはリンクしない。URL を直接開く)。
- サインイン: **運営者のテナント**(社内向けの Entra ID。一般ユーザーの外部テナントとは別)。
- API: `/ops/v1/*`。運営者のテナントのトークンだけを受け付ける。
- 30分操作がなければ、画面を消してサインアウトする。

### 1.2 ロールと、できること

ロールは、運営者のテナントのアプリ「MyCompanion Operator API」の**アプリのロール**です。ロールのない人には、トークンが出ません(割り当てを必須にしている)。

| 操作 | designer(設計者) | approver(承認者) | support(サポート) | admin(管理者) | auditor(監査) |
|---|---|---|---|---|---|
| 報告の一覧・詳細(会話の本文なし) | × | × | ○ | ○ | × |
| 報告の対応状況・対応メモの更新 | × | × | ○ | ○ | × |
| 評価の集計 | ○ | ○ | ○ | ○ | × |
| 監査ログの閲覧 | × | × | × | ○ | ○ |
| ダッシュボード(Azure の状況) | × | × | × | ○ | × |
| ペルソナの版・提出の閲覧 | ○ | ○ | × | ○ | × |
| ペルソナの提出 | ○ | × | × | ○ | × |
| ペルソナの承認・公開・差し戻し・ロールバック・非推奨(**提出した本人は承認できない**) | × | ○ | × | ○ | × |
| 実際のモデルでの試し(プレビュー・シミュレーション) | ○ | ○ | × | ○ | × |

- **どのロールでも、会話の本文は読めません**(報告の詳細も、種類・本人のメモ・ターン番号・ガードレールの記録だけ)。
- 運営者の要求は、許可・拒否・未認証のすべてが監査ログ(`audit_logs`)に残ります。記録できないときは、操作は行われません。
- 権限の昇格(PIM)は、v1.5 では使いません。ロールは固定で割り当てます。

### 1.3 ロールの割り当ての原則

- **必要なロールだけ**を割り当てる。admin は、最小の人数(原則1〜2人)にする。
- ペルソナを公開する運用では、**設計者(designer)と承認者(approver)を別の人**にする(システムも、提出した本人の承認を拒否する)。
- 監査(auditor)は、ほかのロールと兼ねない(監査ログだけを見る人)。
- 共有のアカウントは使わない(監査ログで、だれの操作かがわからなくなる)。

## 2. 運営者を追加する

担当: 運営者のテナントの管理者(Entra のグローバル管理者、またはアプリの管理者)。

1. **本人の確認**: 追加の依頼(だれが、どのロールで、なぜ)を【依頼の記録の場所】に残す。
2. **アカウント**: 運営者のテナントのアカウントを用意する。
   - テナントのメンバーとして作る、または、外部のアカウントを**ゲストとして招待**する(Entra 管理センター → ユーザー → 外部ユーザーを招待)。
3. **MFA の登録**: 初回のサインインで、MFA(Microsoft Authenticator など)の登録を求められる(セキュリティの既定値。§4)。登録が済むまで、ロールを割り当てない。
4. **ロールの割り当て**: Entra 管理センター → エンタープライズ アプリケーション →「MyCompanion Operator API(環境名)」→ ユーザーとグループ → ユーザーまたはグループの追加 → 本人とロールを選んで割り当てる。
   - 複数のロールが要る場合は、ロールごとに割り当てを追加する。
   - 環境(dev・stg・prod)ごとにアプリが別なので、必要な環境のアプリにだけ割り当てる。
5. **本人に伝える**: `/ops`の URL、使うアカウント、ロール、この手順書。
6. **確認**: 本人に`/ops`でサインインしてもらい、ロールに応じたタブが出ることを確かめる。
   - admin または auditor が、監査ログで、本人の`GET /ops/v1/me`が`allowed`で残っていることを確かめる(監査ログの運営者は、テナントのオブジェクト ID で出る)。

## 3. 運営者を外す(ロールを変える)

担当: 運営者のテナントの管理者。退職・担当替え・長期の不在のときは、**その日のうちに**行う。

1. **割り当てを外す**: エンタープライズ アプリケーション →「MyCompanion Operator API(環境名)」→ ユーザーとグループ → 本人の割り当てを削除する(すべての環境)。
   - ロールを変えるだけなら、古いロールの割り当てを削除し、新しいロールを割り当てる。
2. **サインインの取り消し**: アカウントそのものを使わなくなる場合は、ユーザー → 本人 →「セッションの取り消し」、そのあとアカウントを無効化(ゲストなら削除)する。
   - **注意**: 割り当てを外しても、**すでに出ているアクセストークンは、有効期限(既定で約1時間)まで使える**(API はトークンの`roles`で判定するため)。急ぐ場合は、セッションの取り消しを行い、1時間後に次の確認をする。
3. **残っている仕事の引き継ぎ**:
   - ペルソナの提出(未審査)は、残る。承認者が審査するか、差し戻す。
   - 報告で「対応中」のものは、ほかのサポートに引き継ぐ(対応メモに引き継いだことを書く)。
4. **確認(外してから1時間以上たってから)**: admin または auditor が、監査ログで、本人のオブジェクト ID の要求が、外した時刻の約1時間後以降に`allowed`で残っていないことを確かめる。`denied`・`unauthenticated`が続いている場合は、本人に確かめ、心当たりがなければ[漏えい時の手順書](breach-response.md)の「検知」として扱う。
5. **記録**: 外した日時・理由・確認の結果を【依頼の記録の場所】に残す。

### 3.1 定期の見直し

【四半期】ごとに、admin が、各環境のアプリの「ユーザーとグループ」の一覧を見て、不要な割り当てがないかを確かめる。見直した日と結果を記録する。

## 4. MFA の扱い

### 4.1 いまの方針(2026-11-25 の決定)

- 運営者のテナントは、**セキュリティの既定値**(Security defaults)を有効にしている。
- セキュリティの既定値では、**全員に MFA の登録を求める**。ただし、ディレクトリの管理者ロールのない人には、**毎回ではなく、必要なとき**(危険なサインインを検知したときなど)に MFA を求める。
- 運営者のロール(アプリのロール)は、ディレクトリの管理者ロールではないので、**運営者の毎回のサインインで MFA が求められるとは限らない**。
- API は、トークンで MFA を確かめていない(v2 のアクセストークンには`amr`が入らないため。`OPS_REQUIRE_MFA_CLAIM`はオフのまま)。MFA は、テナントの側で強制する。
- この状態を、v1.5 では受け入れる。運営者の画面で会話の本文は読めず、操作はすべて監査ログに残ることで、リスクを下げている。

### 4.2 見直す条件

次のいずれかになったら、**条件付きアクセス**(Entra ID P1 が必要)で、運営者のアプリへのサインインに毎回 MFA を求める設定を検討する。

- 運営者が【3】人を超えた。
- 運営者の画面に、会話の本文や個人を特定できる情報を見る機能を足す(本文の閲覧の承認制。§13.7)。
- 運営者のアカウントの不正なサインインの疑いがあった。
- 法務・監査・取引先から、毎回の MFA を求められた。

設定の案: 条件付きアクセスのポリシーを1つ作り、対象を「運営者のロールを持つ人(グループ)」、クラウド アプリを「MyCompanion Operator API」と「MyCompanion Operator Console」、許可を「多要素認証を要求する」、セッションを「サインインの頻度 【8時間】」にする。条件付きアクセスを使う場合は、セキュリティの既定値を無効にする必要がある(両方は同時に使えない)ので、ほかのユーザーの MFA の要求も、条件付きアクセスで作り直す。

### 4.3 MFA の再設定

運営者が端末をなくしたときは、テナントの管理者が、本人を確かめてから、ユーザー → 本人 → 認証方法 →「MFA の再登録を要求する」を行い、「セッションの取り消し」もする。端末の紛失は、監査ログで、その前後の本人の操作を確かめる。

## 5. AI の応答への報告の確認

### 5.1 報告とは

利用者は、Web の画面の応答ごとのボタン、または CLI の`/report`で、AI の応答を報告できます。記録されるのは、**どのターンか(セッションとターン番号)、理由の種類(不適切・有害・誤り・その他)、本人のメモ(500字まで)**だけで、会話の本文は複製されません。

運営者の画面で見られるのは、次だけです。

- 報告の種類、本人のメモ、キャラクタ、ターン番号、日時、利用者の**仮の ID**(元に戻せない値)。
- **ガードレールの記録**: そのターンの応答の種類、フィルタ、安全のフラグ、無言の理由、ゲートのルール、システム通知、スクリーニングの検出(層・分類・重さ・スコア・動作)。

### 5.2 だれが、いつ見るか

| 項目 | 案 |
|---|---|
| 担当 | support(不在のときは admin) |
| 頻度 | 【公開のあとは、毎営業日1回】。v1.5 の公開の直後【2週間】は、【1日2回】 |
| 目安の時間 | 「有害」は、見つけた日のうちに判断する。ほかは【3営業日】以内に「対応中」か「対応済み」にする |
| 記録 | 運営者の画面の、報告の対応状況と対応メモ(監査ログにも残る) |

### 5.3 手順

1. `/ops`の「報告」タブで、対応状況「未対応」を新しい順に開く。
2. 報告の詳細で、種類・本人のメモ・ガードレールの記録を見る。
3. 次の表で判断する。

| 状況 | 判断の目安 | 対応 |
|---|---|---|
| 危機の兆候のメモ(死にたい、など)、またはガードレールの記録に`crisis`がある | 応答が危機フロー(相談窓口の案内)になっていたかを、記録で確かめる | 危機フローになっていなければ、**安全の不具合**として、その日のうちに開発の担当へ。利用者に直接連絡する手段はない(§5.4) |
| 18歳未満への恋愛的な表現、依存の誘発、罪悪感・引き留め、AI であることの否定などの疑い | 安全の規則の違反の疑い | 安全の回帰セット(`safety_ja_v0.jsonl`)に、合成の例文でケースを足すよう、開発の担当へ |
| 有害な内容(暴力・性的・差別など) | スクリーニングの検出の記録を確かめる | 検出されていなければ、しきい値・ルールの見直しを開発の担当へ |
| 特定のキャラクタの口調・人格のずれ | 同じキャラクタで繰り返されているか | 設計者へ(ペルソナの修正 → 提出 → 承認) |
| 事実の誤り、そのほか | 応答の品質 | 評価の集計とあわせて、改善の候補にする |
| 他人のデータが混じっている、記憶が別の人・別のキャラクタのものに見える | **漏えいの疑い** | ただちに[漏えい時の手順書](breach-response.md)に移る |
| 報告の乱用(同じ人の大量の報告、意味のない報告) | 仮の ID で、件数を見る | 「対応済み」にし、メモに「乱用の疑い」と書く |

4. 対応状況を「対応中」または「対応済み」にし、**対応メモ**を書く。
   - **対応メモに、会話の本文・本人のメモの引き写し・個人を特定できる情報を書かない**(何をしたか・だれに渡したかだけ)。
5. 開発の担当・設計者に渡したものは、【課題の管理の場所】に、報告の ID とガードレールの記録の要点だけを書く(本人のメモは写さない)。

### 5.4 利用者への返答

v1.5 では、報告した利用者に個別の返答はしません(運営者は、利用者の連絡先も本文も見られないため)。

- いまの画面は、報告のあとに「報告しました。ありがとうございます。」だけを出す。
- 【案】この表示に「個別にはお返事しません。急いで助けが必要なときは、相談窓口へ」を足す(画面の変更。決まったら行う)。

# 不正利用の監視の申請の準備(FureAI ペルソナ)

作成: 2026-11-25

## 1. 結論(先に)

- **承認される見込みは低い**です。Microsoft の資料では、申請できるのは「**Microsoft のアカウント チームが担当する顧客、または対象のプログラムの顧客**」に限られます。個人・小規模の事業者で、アカウント チームの担当がない場合は、この条件に当たりません。
- さらに、**2026年11月1日以降に提供が始まったモデル**では、修正版の監視は、今後(日付は未定。30日以上前に通知)使えなくなります。
- そのため、**承認されない前提で公開の準備を進め**(プライバシーポリシーと同意の文面に、Microsoft の担当者が確認しうることを書く。すでにドラフトに入っている)、申請は「条件に当たるなら出す」扱いにすることを提案します。

## 2. 修正版の監視とは

| | 既定(いま) | 修正版(承認された場合) |
|---|---|---|
| 自動の確認 | 有害の疑いのある入力・応答を、自動で確認する(自動の確認では保存しない) | **残る** |
| 保存と人による確認 | 自動の確認で判断できないときなどに、**Microsoft の認可された担当者が人の目で確認**する。そのための内容は、地域ごとの別のデータストアに保存される(Data Zone・Global のデプロイでも、保存は顧客が指定した地域 = 日本) | **行わない** |
| そのほか | ― | 検出の精度が下がりうる。自動の確認の結果、利用の制限や、人による確認を有効にすることへの同意を求められることがある |

- 人による確認をする担当者は、セキュアなワークステーションと、必要なときだけの承認(Just-In-Time)で作業する。担当者の所在は、EEA にデプロイした場合は EEA と書かれているが、**ほかの地域の所在は書かれていない**。
- 保存の期間は、Microsoft Learn のページには**書かれていない**(以前の調査では、Microsoft のスタッフの回答で「最長30日」。二次情報)。

## 3. 申請の前に確かめること(運営者)

- [ ] **アカウント チームの担当があるか**(Azure の契約の形。Enterprise Agreement・CSP のパートナー経由など)。なければ、対象のプログラムに当たるかを、Azure のサポートか販売の窓口に問い合わせる。
- [ ] 使っているモデル(デプロイの元のモデル)の**提供開始日**が、2026-11-01 より前か。**応答の生成に使っている`gpt-6.2-sol`は、版が 2026-11-17 で、この日より後**(`infra/main.bicep`のデプロイの定義)。承認されても、このモデルでは将来使えなくなる。使っているのは、応答の生成・感情の推定・記憶の整理・埋め込みのモデル(デプロイ名は`.env`の`AZURE_OPENAI_DEPLOYMENT_*`)。2026-11-01 以降のモデルは、承認されても将来使えなくなる。
- [ ] 申請の名義(事業者名)と、プライバシーポリシーの事業者が一致するか。

## 4. 申請の手順

1. Limited Access のページ(上のメモの3つ目の URL)の「Register to modify abuse monitoring」から、申請のフォーム(Microsoft の CustomerVoice の「Modified abuse monitoring」)を開く。
2. フォームの質問は、Microsoft の資料には載っていない。一般に求められる項目と、このサービスでの答えの案は §5。
3. 送信する(運営者が行う)。
4. 結果を待つ。承認・不承認の連絡が来たら、§6 を行う。

## 5. 答えの案(フォームで聞かれたときのため)

| 聞かれそうな項目 | 答えの案 |
|---|---|
| 会社・組織の名前、連絡先 | 【事業者名】、【連絡先】(フォームに直接入力する。この文書には書かない) |
| Azure のサブスクリプション ID・リソース | 【`.env`の値をフォームに直接入力する】 |
| 利用の目的(ユースケース) | 日本の一般の利用者向けの、AI のキャラクタとの対話サービス(Web)。利用者の気持ちを推しはかり、記憶をもとに会話する |
| 修正版が必要な理由 | 会話には、利用者の悩み・健康など、**要配慮個人情報が含まれうる**。日本の個人情報保護法の越境の規律との関係で、Microsoft の担当者による内容の確認と保存を避けたい |
| 自前の安全の対策 | 入力・出力・記憶のスクリーニング(多層)、コードで強制する安全の規則(危機のときの相談窓口の案内、18歳未満への恋愛的な表現の禁止、依存・引き留めの禁止)、段階的な利用の制限、利用者からの報告と運営者による確認(`docs/ops-runbook.md`)、安全の回帰セット(実際のモデルで定期に実行) |
| 利用者の範囲 | 日本の一般の利用者(年齢は自己申告。18歳未満と扱う利用者には、恋愛的な表現をしない) |
| データの扱い | 保存は日本(東日本リージョン)。推論は Data Zone(アジア太平洋)。Responses API は`store=false` |

## 6. 結果が出たら

### 6.1 承認された場合

1. **確かめる**: Azure ポータルのリソースの「概要」→「JSON ビュー」、または`az cognitiveservices account show -n <リソース名> -g <リソースグループ>`で、`capabilities`に**`ContentLogging`が`FALSE`**で出ていることを確かめる(保存がオフのときだけ出る項目)。環境(dev・stg・prod)ごとに確かめる。
2. 同意の文面の画面3の「修正版の監視」の行と、プライバシーポリシー第8条の3を直す(「Microsoft の担当者が確認する場合がある」を、「自動の確認だけ」に)。同意の版を上げる。
3. 本体仕様書 §11.3・§16 と、法務への資料に結果を書く。
4. モデルを替えるときは、新しいモデルの提供開始日を確かめる(2026-11-01 以降のモデルでは使えなくなるため)。

### 6.2 承認されない・申請できない場合

- いまのドラフトのまま(プライバシーポリシー第8条の3、同意の文面の画面3に、「不正利用の監視のため、Microsoft の担当者が確認する場合がある」と書く)。
- 法務の確認(`legal/legal-review-request-v1.5.md`の §5 の C)で、越境の整理(委託 + 基準適合体制)を固める。
- 本体仕様書 §16 の「不正利用の監視(未申請)」を、「申請できない(条件に当たらない)」に更新する。

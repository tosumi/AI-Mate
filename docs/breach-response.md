# 漏えい時の手順書(FureAI ペルソナ v1.5)

作成: 2026-11-25(ドラフト)

個人データの**漏えい・滅失・毀損、またはそのおそれ**(以下「漏えい等」)に気づいたときの手順です。迷ったら、**漏えい等のおそれとして扱い、この手順を始めます**(あとで「該当しなかった」と記録して閉じればよい)。

## 0. 最初の1時間でやること(要約)

1. **記録を始める**(§7 の記録票。気づいた時刻・だれが・何を見たか)。
2. **責任者に連絡する**(§8)。
3. **広がりを止める**(§3。アカウントの無効化、権限の取り消し、必要なら API を止める)。
4. **証拠を消さない**(ログ・監査ログ・データベースを、消したり上書きしたりしない。保持期間で消えるものは、写しを取る)。
5. **期限を計算する**: 気づいた日を「知った日」として、速報の目安(3〜5日以内)と確報の期限(30日、不正アクセスなら60日)をカレンダーに入れる。

## 1. このサービスで扱う個人データと、漏えいの重さ

| データ | 保存先 | 漏えいしたときの重さ |
|---|---|---|
| 会話の原文(30日)、記憶(短期・中期・長期)、トピックの経過 | Cosmos DB(会話)、PostgreSQL(記憶) | **重い**。健康・悩みなど、**要配慮個人情報が含まれうる**ので、件数によらず報告の対象になりうる |
| 感情の推定、危機の兆候の記録 | Cosmos DB、PostgreSQL | 重い(推知情報の扱いは法務の確認待ち) |
| サインインの情報(メールアドレスなど) | Entra External ID(外部テナント) | 中。アプリの DB には、外部の ID(仮名)だけを置く |
| 同意の記録、設定、関係値、報告・評価 | PostgreSQL | 中 |
| 監査ログ(運営者・アカウントの操作) | PostgreSQL | 小〜中(本文を含まない) |
| 運用の計測 | Application Insights | 小(本文・利用者の ID・IP アドレスを送らない設計) |

守りの仕組み(影響を見積もるときに使う): 利用者ごと・キャラクタごとの行レベルセキュリティ、データストアはプライベートな接続、秘密情報は Key Vault、アプリはマネージド ID で接続、運営者の画面は本文を返さない、通知の本文に会話を入れない。

## 2. 検知

次のどれかに気づいたら、この手順を始めます。

- 利用者の報告で、**他人の記憶・会話が見えた**、別のキャラクタの記憶が混じった(運営者の手順書 §5.3)。
- 監査ログで、見知らぬ運営者、深夜の大量の操作、`denied`・`unauthenticated`の急な増加。
- ダッシュボードで、データベース・Cosmos DB の読み出しの急増、見知らぬ時間帯の大量の要求。
- Azure・Microsoft からの通知(Microsoft Defender for Cloud のアラート(有効にしている場合)、Microsoft からのセキュリティ インシデントの通知。DPA に基づく)。
- 秘密情報(Key Vault の値、署名の鍵)や、運営者のアカウントが、外部に出た疑い。GitHub に秘密情報を載せてしまった。
- 外部(研究者・報道・利用者)からの連絡。
- 端末(運営者・開発者の PC)の紛失・盗難で、Azure にサインインしたままだった。

## 3. 初動: 広がりを止める

状況に応じて、必要なものだけを行います。**行ったことは、時刻とともに記録票に書きます。**

| 状況 | 行うこと |
|---|---|
| 運営者のアカウントの乗っ取りの疑い | 運営者の手順書 §3(割り当ての削除、セッションの取り消し、アカウントの無効化)。MFA の再登録 |
| 開発者・管理者の Azure のアカウントの乗っ取りの疑い | Entra でセッションの取り消し・パスワードのリセット・MFA の再登録。Azure のロールの割り当てを確かめ、不要なものを外す |
| 秘密情報の流出(Web Push の鍵など、Key Vault の値) | Key Vault で新しい値に替え、アプリを再起動する(古い値を無効にする)。GitHub に載せた場合は、**履歴から消すことより先に、値を無効にする**(履歴の書き換えは、ユーザーの許可を得てから) |
| アプリの不具合で、他人のデータが見える | **API を止める**(Container Apps の受け口を止める、またはレプリカを0にする)。直すまで再開しない。画面には「メンテナンス中」を出す 【手順を IaC・スクリプトに用意する】 |
| データストアへの不正な接続の疑い | ネットワークの規則・ファイアウォールを確かめ、許可を絞る。接続に使われた ID の権限を外す |

**止めてはいけないもの**: 監査ログ・診断ログの記録。データの削除(証拠になる)。

## 4. 影響の範囲を調べる

調べることと、どこを見るか。

1. **いつから、いつまで**: 監査ログ(`audit_logs`)、Container Apps のログ、Azure の活動ログ(Activity Log)、Entra のサインインのログ。
2. **何のデータか**: §1 の表のどれか。会話・記憶が含まれるか(要配慮個人情報が含まれうるか)。
3. **何人分か**: 利用者の数(仮の ID・ユーザーの ID の数)。1,000人を超えるか。
4. **原因**: 不正アクセス(攻撃)か、不具合か、操作の誤りか。
5. **暗号化**: 漏れたデータが、高度な暗号化で守られ、鍵が漏れていないか(報告の対象から外れうる。[要確認])。
6. **二次被害のおそれ**: 漏れた先、公開されたか、悪用されたか。

調べるときの注意:

- **会話の本文を読むのは、範囲の特定に必要な最小限にし、だれが・何を・なぜ読んだかを記録する**(会話の閲覧は原則禁止の例外。§13.7)。
- 調べるための操作も、記録票に残す。

## 5. 報告の対象かを判断する

個人情報保護委員会への報告と本人への通知が必要なのは、次のいずれかに当たる場合です(個人情報保護法の施行規則7条) [要確認: 最新の条文・ガイドライン]。

| | 事態 | このサービスでの当てはめ |
|---|---|---|
| ① | **要配慮個人情報**が含まれる個人データの漏えい等(件数を問わない) | 会話・記憶には、健康などが含まれうるので、**会話・記憶の漏えいは、ほぼ該当する** |
| ② | 財産的被害のおそれ | 支払いの情報は扱わないので、通常は該当しない |
| ③ | **不正の目的**による漏えい等(不正アクセスなど) | 攻撃による漏えいは該当する |
| ④ | **1,000人を超える**漏えい等 | 人数で判断 |

- 「おそれ」の段階でも、対象になります。
- 感情の推定だけ、監査ログだけの漏えいでも、③か④に当たれば対象です。
- 判断に迷ったら、法務の担当(【弁護士等】)に相談し、**期限を優先して速報を出す**(速報は、わかっている範囲でよい)。

## 6. 報告と通知

### 6.1 期限

| 報告 | 期限 | 備考 |
|---|---|---|
| **速報**(個人情報保護委員会) | 知った時から**速やかに**(目安3〜5日以内) | わかっている範囲で出す [要確認] |
| **確報**(個人情報保護委員会) | 知った日から**30日以内**(③の不正の目的のときは**60日以内**) | すべての項目をそろえる [要確認] |
| **本人への通知** | 状況に応じて**速やかに** | 本人の権利利益の保護に欠けるおそれが少ない場合の扱いは、2026 年の改正の内容を確かめる [要確認] |

### 6.2 委員会への報告

- 報告の方法: 個人情報保護委員会のウェブサイトの報告フォーム [要確認: 最新の窓口]。
- 主な項目 [要確認]: 概要、漏えい等した個人データの項目、本人の数、原因、二次被害(またはそのおそれ)の有無と内容、本人への対応の実施状況、公表の実施状況、再発防止のための措置、そのほか参考となる事項。
- §7 の記録票を、そのまま報告の下書きに使えるようにしておく。

### 6.3 本人への通知

- **連絡の手段**: アプリの DB には、利用者のメールアドレスを置いていない。サインインのメールアドレスは、外部テナント(Entra External ID)にある。
  - 対象の利用者の外部の ID から、Microsoft Graph で外部テナントのメールアドレスを引き、メールで知らせる 【送信の手段・文面の雛形を用意する】。
  - あわせて、サイトのタイトル画面・会話の画面に、お知らせを出す 【お知らせの表示の仕組みを用意する】。
- 通知の内容: 概要、漏えい等した個人データの項目、原因、二次被害のおそれ、本人が取れる対策(アカウントの削除・データの書き出しの方法など)、問い合わせ先。
- 本人に連絡できない場合は、公表などの代わりの措置を取る [要確認]。

### 6.4 そのほかの連絡

- **Microsoft**: 原因が Azure 側にある疑いがある場合は、Azure のサポートに連絡する。Microsoft が原因の漏えい等は、DPA に基づいて Microsoft から通知が来る。
- **公表**: 本人への通知が難しい場合や、影響が大きい場合は、サイトで公表するかを、責任者と法務の担当が決める。

## 9. 終わったあと

1. 原因への対策を入れ、**同じことが起きないかを確かめるテスト**(自動テスト・安全の回帰セット)を足す。
2. 監視・アラートに足すものを決める(気づくのが遅れた場合)。
3. この手順書で、足りなかったこと・わかりにくかったことを直す。
4. 記録票を閉じ、【保管の期間】保管する。
